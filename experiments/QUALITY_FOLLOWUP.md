# Context quality and correction workflow

**Historical experiment before the real-title training release; no accuracy gain was established at this stage.** The earlier tenfold WordNet lookup gives lexical cues but has not raised accuracy. To investigate the remaining errors without contaminating evaluation, `specificity_trial.mjs` fitted a small residual context/specificity feature head on the **786 base training rows only** (20 prespecified regularisation/extra-row weighting settings; the best original-validation setting used no synthetic supplement rows). The best setting raised the *already inspected* original validation from **97/102 (FP 2, FN 3)** to **100/102 (FP 1, FN 1)**, and expanded validation from **163/168** to **166/168**. After that choice, the protected test and developer-authored probes showed **168/170 → 167/170** on expanded held-out tasks and **35/40 → 34/40** on unfamiliar contexts. That head is **rejected, not bundled**. Selecting another variant after looking at those test results would be test-set tuning. These small, repeatedly inspected, synthetic-heavy partitions do not establish deployment accuracy.

The practical issue we fixed at that stage instead was **how the model learns corrections**. Previously, adding a browser example silently disabled its 2,900 supplemental training rows and the earlier 45% task anchor, and reshuffled the base examples (which could move a held-out row into training). On the untouched default corpus, new non-duplicate examples now go to a **training-only feedback partition**. The original 1,124 base rows are split with seed 1 before feedback is appended to the 786 base training rows and 2,900 supplemental training rows (the later real-title release adds 131 more training-only rows). The 168 validation and 170 test rows stay in their original partitions. Exact and punctuation-only duplicates of any base or supplement example are refused; changing the seed or ratios while feedback is present is refused. The task prior and 45-slot offline lexical head are retained. Imported corpora remain independent: they get their own split, no task-specific supplement, anchor or lexical prior.

To correct a prediction in `index.html`: score a task, click **Actionable** or **Generic / filler** under the score, then click **Train model**. The correction is not applied until retraining finishes. **Download feedback** saves `task_feedback.json`; **Import feedback** restores those rows into the default task's training-only partition, refusing duplicates atomically. The page doesn't silently persist corrections. Do not put test or validation text into this file. Importing a *combined dataset* with the separate Import JSON button is *not* equivalent to importing training-only feedback; it makes a new split. Browser smoke demonstrates a single manually authored correction: “Rebuild core_runtime.so for arm64” (actionable) changed from **0.660 to 0.435** in the historical checkpoint (the current real-title checkpoint yields a different score) at 40 epochs while the same 170 original held-out rows scored **98.8% before and after**. This shows the correction can be learned; it does **not** show generalisation to new examples or real-world improvement.

For repeatable CLI training from a downloaded feedback file (on top of the original training-only supplement):

```sh
node train.mjs --extra experiments/task_supplement.json \
  --feedback experiments/real_issue_training.json --feedback task_feedback.json \
  --anchor-model experiments/task_baseline_model.json --anchor-mix 0.5 --out model.json
node experiments/assemble_lexicon_model.mjs   # bundle the existing 45-slot lexical head
npm run test:feedback && npm run test:model && npm run test:app
```

The CLI rejects feedback that duplicates any base, supplemental or other feedback row (ignoring punctuation/case) and refuses a different split seed with the task anchor. It records feedback count and source in the model metadata. A file of one or two corrections can overfit or degrade other inputs; verify with a separate, human-labelled validation set drawn from the actual application. Real-world task and commit text with author/project-diverse, independently held-out labels is still needed. A text-only commit message score cannot verify author, truth or correspondence with a diff.
