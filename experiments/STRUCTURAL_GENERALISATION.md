# Structural feature trial — promising transfer, failed release gate

**Historical decision: do not ship the original `structureVersion: 1` candidate.** Its comparison reference was the 50%-anchored issue-corrected v4 model (524,289 trainable scalars, 60,167 nonzero weights, 2,634,540 bytes). The first structural trial failed its predeclared floor; its later confirmation results could not reverse that decision. A **different evidence-gated version 3** was subsequently fitted and evaluated on a new, previously unopened set; it is now the default. See [the version-3 release report](STRUCTURE_V3_RELEASE.md). Version-1 diagnostics here remain historical, not a description of today's `model.json`.

## Question, design, and partitions

The previous model heavily overflagged meaningful GitHub issue titles. To test whether *shape* transfers beyond memorised terms, the opt-in v4 encoder maps words to abstract roles (failure, condition, action, vague, function, target, number and punctuation), emits adjacent/triple role patterns and cues for failure/condition, action/target, code-like identifiers and vague-without-target patterns. Unknown technical nouns generally become `TARGET` rather than sharing a generic OOV word representation. These features use the existing position/affix hash banks; there is no second classifier, changed threshold or extra parameter. The cue lists still contain known English words and are not semantic understanding or fully vocabulary-free; role assignment, tokenization, mixed-language text, negation and project-specific conventions remain limitations. Hash collisions are possible. The training examples and score labels are otherwise identical to the corrected model.

The candidate was fitted on the same **3,928 training rows** (786 original train, 2,900 synthetic supplemental, 131 attributed prior issues and 111 previously inspected Fastify/ESLint corrections). A 0.4 anchor was selected on previously inspected original-task/Axios validation plus new **Vitest** issue/commit selection rows; 0.4 was then frozen. The source pages, URLs, labels and excluded ambiguous rows are in `structure_selection.json`. Before scoring the first locked set, `structure_locked.json` was saved from **Home Assistant, Flutter and Playwright issues, Deno commit subjects**. `structure_partition_guard.mjs` checks source/label counts, source URLs, duplicates against training and prior probes, and cross-partition near-duplicates. The 152 collected titles comprise 146 clear rows and 6 unclear. Sources were chosen by project and API page, **not randomly sampled**. Labels were assigned by one rater from short title/subject text only; `genuine` means informative *under the task/commit policy*, not authentic or valid. A commit subject was not checked against its diff. In particular, the clear rows are strongly imbalanced toward genuine text.

First-locked project accuracy: Home Assistant 12/24 → 15/24; Flutter 13/29 → 21/29; Playwright 22/36 → 30/36; Deno subjects 38/57 → 46/57. The *predeclared* release rule also required **at least 168/170** on the already-inspected expanded task set; the candidate scored **167/170**, introducing a false positive on **“Take the last pastry.”** The first locked trial printed `FAIL — keep existing model`, so **it is not a release**. No second anchor, threshold or cue list was selected on that now-opened set.

After that failure, a separate confirmation set was labelled from Rust and CPython issues and Flask commit subjects. It was never used to choose the feature recipe or mix; it was saved *after seeing the failed first gate*, so it cannot be called a fresh release test for a new selection rule. One duplicated old training title was marked unclear before confirmation scoring; the partition guard was rerun successfully. Of 109 titles, 85 have clear labels (56 issues, 29 commit subjects); there are only **four** clear vague titles. The frozen candidate scored 54/85 → 67/85, FP 30 → 17, FN 1 → 1: Rust 14/28 → 22/28, CPython 22/28 → 25/28, Flask subjects 18/29 → 20/29. This supports investigating the structural hypothesis, **not replacing the failed gate**. The confirmation set is now inspected too.

Across the 231 clear first-locked and confirmation rows, stratifying by tokens missing from the 3,928-row *training vocabulary* gives 76/106 → 90/106 for <25% OOV (FP 25 → 12, FN 5 → 4), and 63/125 → 89/125 for ≥25% OOV (FP 61 → 34, FN 1 → 2). These are post-hoc descriptions from already-opened sets, not a new validation criterion. The second group still has 34 false positives. A local 1,000-prediction timing check was ~187 ms for the old model versus ~290 ms for the candidate on the sampled titles; this is one non-browser machine run, not a latency guarantee. The candidate has the same 524,289-parameter capacity. All title accuracy figures above are conditional on single-rater, ambiguity-filtered, selected pages and **must not be represented as deployment accuracy**.

## Reproduction and next step

`node train.mjs --structure --extra experiments/task_supplement.json --feedback experiments/real_issue_training.json --feedback experiments/issue_corrections_training.json --anchor-model experiments/task_baseline_model.json --anchor-mix 0.5 --out .cache/structure-candidate-050.json && node experiments/assemble_lexicon_model.mjs .cache/structure-candidate-050.json` recreates the training-only candidate used by `structure_selection_trial.mjs` (the trial reconstructs other mixes without training on selection rows). `node experiments/structure_partition_guard.mjs` checks all three partitions; `node experiments/structural_benchmark.mjs` prints descriptive old-versus-candidate results from the inspected datasets. `structure_locked_trial.mjs` retains the *original* gate; `structure_confirmation_trial.mjs` prints confirmation diagnostics but **never saves a release checkpoint**. `.cache/` is excluded from Git. Running these scripts again cannot make the tests fresh.

That future version-3 candidate was selected without rescoring these inspected partitions during development and passed the unchanged task floor plus a separately frozen four-project diagnostic. It is documented in `STRUCTURE_V3_RELEASE.md`. Its new test also has too few vague titles and single-rater labels; independent, multiply annotated data with both classes is still needed before any deployment-accuracy claim.
